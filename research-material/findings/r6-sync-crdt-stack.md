# R6 — Sync / CRDT / Transport / Local-First Infrastructure Stack

Lane: sync, CRDT, transport, local-first infrastructure. Research date: 2026-10-26. Every claim carries its source URL in parentheses. Where a claim could not be verified this pass, it is marked UNVERIFIED (that is a real finding, not a gap to paper over).

Context for all pull-from assessments: a local-first notes app in Rust/Tauri with zero-knowledge (E2EE) ambitions. Target scale: 10k+ documents, offline for days, then merge. Licenses: GPL/AGPL items are treated as concepts-only (study, do not link code).

## 0. Cross-cutting finding first: can a CRDT that reads plaintext operations be combined with E2EE?

Short answer: yes, and every serious project in this stack has now converged on the same family of answers. The question is no longer "is it possible" but "which metadata leaks remain and which group-encryption scheme you bolt on." The evidence, per project:

- The classic tension: CRDT algorithms (YATA, RGA, Automerge's columnar op-log) operate on structure: op IDs, actor IDs, insertion positions, tombstones. A naive "encrypt each character's payload" approach still leaks structure (document length, edit patterns, number of edits, actor counts), and some CRDTs genuinely need to compare plaintext to compute merge order. A widely-read practitioner writeup frames exactly this: local-first + E2EE means the source of truth is local ciphertext, and the hard part is what the merge algorithm itself must see (https://kerkour.com/crdt-end-to-end-encryption-research-notes, Dec 2025).
- **Automerge**: its dedicated p2p sync protocol (Beelay) was explicitly designed so that "this protocol will work for any data structure which likes being represented as a hash-linked DAG of changes" and "because one of the goals of the project is to produce a sync protocol which allows end-to-end encryption of the document data" (https://github.com/automerge/beelay). The successor layer, Keyhive, adds access control + E2EE with a group key agreement (BeeKEM) on top of Automerge and other CRDTs (https://www.inkandswitch.com/project/keyhive/, https://automerge.org/blog/2026-september/).
- **Yjs**: no built-in E2EE in the core; the maintainers' community threads (2020 and 2024) show the practical recipe is encrypt payloads/updates at the provider layer, because Yjs updates are opaque byte strings once created; open threads also show the unsolved edges (awareness/cursor data, metadata) (https://discuss.yjs.dev/t/implementing-end-to-end-encryption/308, https://discuss.yjs.dev/t/y-text-and-end-to-end-encryption/2854). Sealing whole updates (snapshot-or-update blobs) works because Yjs does not need the server to understand the content; that is the design secsync industrialized (https://github.com/nikgraf/secsync).
- **Loro**: ships an official wire protocol with an E2EE mode, explicitly marked experimental: "End-to-end encrypted Loro is included in loro-protocol, but the feature is currently experimental: expect wire formats and key-management APIs to change, and do not rely on it for production-grade security audits yet" (https://loro.dev/blog/loro-protocol, Oct 2025). The Rust crate mirrors the TS package and implements the E2EE flow documented in protocol-e2ee.md (https://crates.io/crates/loro-protocol).
- **any-sync**: the strongest existence proof that "CRDT-native AND E2EE-native" is a solved product problem: data is stored as encrypted DAGs, every change cryptographically signed, each device independently applies and verifies CRDT updates (https://github.com/anyproto/any-sync). It ships today inside Anytype with millions of objects synced.
- **p2panda**: treats this as its core research area: dedicated crates for decentralized group encryption with post-compromise security and optional forward secrecy (p2panda-encryption) and multi-device group data encryption (p2panda-spaces) (https://github.com/p2panda/p2panda).
- **A production reference implementation at note-app scale exists now**: IlowObsidianSync, an Obsidian plugin, encrypts Loro CRDT updates client-side with AES-256-GCM before a self-hosted Go/PostgreSQL relay stores them; "the server only ever stores ciphertext" (https://github.com/Ilow-Space/IlowObsidianSync). This is architecturally almost exactly the target app of this project.

Residual caveats common to all approaches: metadata visible to the relay (who syncs what, when, roughly how much) unless you add ZK machinery; group membership changes need key rotation and snapshot re-encryption; a removed collaborator may keep receiving updates until propagation catches up (https://github.com/nikgraf/secsync documents these limits candidly, https://automerge.org/blog/2026-september/ for Keyhive's written threat model and admitted gaps).

## 1. Automerge

**What it is / who maintains it.** Automerge is "a data sync engine" for local-first apps: a JSON-like CRDT library plus persistence and networking, originating from Ink & Switch and maintained by the Automerge team (Alex Good, Alex Jung and others) as the reference implementation of the "local-first software" research agenda (https://automerge.org/docs/hello/, https://github.com/automerge/automerge). The original JS implementation ("automerge-classic") is retired; "all development effort has shifted to the new implementation which is written in Rust" (https://github.com/automerge/automerge-classic).

**Maturity / current status.** Version 2.0 (Jan 2023) was declared "a production-ready CRDT with huge improvements in performance and reliability, available in both JavaScript and Rust, with TypeScript types and C bindings" (https://automerge.org/blog/automerge-2/). Automerge 3.0 shipped July 14, 2025 (https://automerge.org/blog/automerge-3/). JS releases continue actively into 2026 (v3.4.0-family rev-fragmentation builds appear on the releases page; the repo was updated August 2026) (https://github.com/automerge/automerge/releases, https://github.com/automerge/automerge). The Rust crate `automerge` is at 0.12.0 on crates.io (release ~28 days before this research), MIT license, 43K SLoC, 400 KiB package (https://crates.io/crates/automerge). There is also a monthly "This Month in Automerge" blog, with the September 2026 issue reporting active work on Keyhive and rev-fragmentation (https://automerge.org/blog/2026-september/). Verdict: very active, well-governed, arguably the most "institutionally supported" open CRDT.

**Technical profile.** Core is Rust, exposed to JavaScript via WASM, plus C FFI and bindings for Swift, Python, Java and more (https://github.com/automerge/automerge, https://automerge.org/). Documents are hash-linked DAGs of changes stored in a compressed columnar binary format (https://automerge.org/automerge-binary-format-spec/). Every keystroke gets a unique ID; most of the engineering is managing that metadata at scale (https://automerge.org/blog/automerge-3/). Automerge 3.0's headline: "in Automerge 3.0, we've rearchitected the library so that it also uses the compressed representation at runtime... pasting Moby Dick into an Automerge 2 document consumes 700Mb of memory, in Automerge 3 it only consumes 1.3Mb"; documents with large histories load "much much faster (we recently had an example of a document which hadn't loaded after 17 hours loading in 9 seconds!)" (https://automerge.org/blog/automerge-3/). That 17-hour example is exactly the "offline for days, then merge" failure mode this project worries about, and it is the strongest public evidence of the fix. The `@automerge/automerge` npm package publishes the WASM-based API with TypeScript types (https://www.npmjs.com/package/@automerge/automerge); the wasm binary is shipped both as a .wasm file and as a base64-embedded JS module (https://automerge.org/docs/reference/library-initialization/).

**Bundle size.** A realistic data point from the wild: an Obsidian plugin found its release main.js was 7,651,624 bytes total, of which "Automerge WASM (base64) 4,761,680 bytes, 62.2%" (https://github.com/SystemSculpt/obsidian-systemsculpt-ai/issues/345, Sep 2026). So budget roughly 4-5 MB of payload if you ship Automerge to a JS frontend (Tauri apps are less sensitive to this, but it matters for memory/startup). The Rust crate itself is 400 KiB of crate source (not binary size; binary size UNVERIFIED this pass).

**License / repo.** MIT; core repo https://github.com/automerge/automerge; Rust crate https://crates.io/crates/automerge (MIT confirmed on crates.io).

**Real-world adoption.** Documented: Celonis' developer docs discuss using Automerge in their stack (https://docs.celonis.com/...; surfaced via search, specific page title: Celonis docs "Automerge" hit, treat as secondary confirmation). Roomy (ATProto-based chat) planned to build on Beelay/Keyhive and Automerge's sync: "We don't need to implement our own synchronization algorithm. We can just use the one from Automerge" (https://lobste.rs/s/oqfmhj/, Feb 2025). Ink & Switch's own prototypes (Fission-era apps, the Keyhive notebooks) all run on it. A large production postmortem culture exists via the Automerge blog and Discord; the most famous public performance postmortem is the 2.0 rewrite story itself (https://automerge.org/blog/automerge-2/). I did not find a 2025/2026 production-outage postmortem naming Automerge; none found (finding: no public postmortems located this pass).

**Encryption story.** Core Automerge has no built-in encryption; the project's answer is the layered ecosystem: Beelay's protocol was designed for E2EE of document data over the hash-linked DAG (https://github.com/automerge/beelay), and Keyhive (automerge.org's "access control and encryption layer for Automerge and other CRDTs") now publishes a written threat model, glossary, and admitted design-vs-code gaps as of September 2026 (https://automerge.org/blog/2026-september/). Keyhive uses BeeKEM, a concurrency-friendly continuous group key agreement derived from TreeKEM, to distribute group encryption keys to members concurrently (https://www.inkandswitch.com/project/keyhive/). Practical consequence: you CAN encrypt everything, but you take on the Keyhive/Beelay layer (Rust, still maturing; see its own section below).

**Pull-from assessment (Rust/Tauri notes app).** Strong pull, two viable postures. (a) Rust-native: depend on `automerge` 0.12.0 (MIT, actively released, 43K SLoC) directly in the Tauri backend; automerge-repo's storage/network adapter patterns are portable concepts (https://crates.io/crates/automerge, https://github.com/automerge/automerge). (b) E2EE-first: pull Keyhive + Subduction (Rust workspace) as the access-control/E2EE layer, accepting pre-1.0 churn (https://github.com/inkandswitch/keyhive). Integration cost: moderate; the automerge API surface is well-documented, and a PoC combining automerge + Keyhive/Beelay + iroh + Tauri already exists publicly as prior art (https://www.context-awesome.com/list/n0-computer/awesome-iroh lists a PoC chat app doing exactly that combination). License: MIT, no constraints. Main risks: metadata (op-log size) growth on very long-lived docs, mitigated in 3.0 but worth benchmarking at 10k+ docs.

## 2. Yjs and yrs (the Rust port)

**What it is / who maintains it.** Yjs is the most widely deployed CRDT for collaborative text, created and maintained by Kevin Jahns, built on the YATA conflict-resolution algorithm; "Yjs is a CRDT implementation that exposes shared data types... compatible with the Yjs algorithm and binary protocol" for its Rust port (https://github.com/yjs/yjs, https://github.com/y-crdt/y-crdt). The Rust port is **yrs** ("wires"), a separate effort under the y-crdt org: "A collection of Rust libraries oriented around implementing Yjs algorithm and protocol with cross-language and cross-platform support in mind. It aims to maintain behavior and binary protocol compatibility with Yjs, therefore projects using Yjs/Yrs should be able to interoperate with each other" (https://github.com/y-crdt/y-crdt). Yrs architecture internals are documented by its co-maintainer Bartosz Sypytkowski (https://www.bartoszsypytkowski.com/yrs-architecture/).

**Maturity / current status.** Yjs: extremely mature; the yjs repo shows continuing updates into 2026 (repo data showed updates ~3 weeks before research) (https://github.com/yjs/yjs). Yrs: actively maintained on crates.io; lib.rs shows a May 4, 2026 release event and lists Yrs as "a high performance CRDT implementation based on the idea of Shared Types... a compatible port of the Yjs CRDT" (https://lib.rs/crates/yrs, https://docs.rs/yrs). Exact latest version number for yrs was not captured this pass (crates.io page fetch was blocked); UNVERIFIED: current yrs version, record as "active as of May 2026" (https://lib.rs/crates/yrs).

**Technical profile.** Yjs: shared types (Y.Text, Y.Map, Y.Array), state vectors, two-phase update encoding (update v1/v2), awareness protocol for presence/cursors, providers architecture (y-websocket, y-webrtc, y-indexeddb, etc.) where the core is transport-agnostic (https://github.com/yjs/yjs, https://github.com/yjs/y-webrtc). Yjs is generally regarded in comparisons as the most battle-tested and among the fastest for text at scale; its updates are opaque byte blobs, which is what makes envelope encryption possible (https://www.loro.dev/docs/performance for the benchmark framing; comparison articles treat Yjs as the production-safety baseline). Yrs: same algorithm/protocol in Rust, with "Shared Types," 53-bit safe-integer compatibility mode with Yjs, weak references, and feature flags for Send/Sync observers (https://docs.rs/yrs). Bindings: pycrdt for Python "provides bindings for Yrs, the Rust port of the Yjs framework" (https://y-crdt.github.io/pycrdt/), plus wasm and other FFI targets (https://github.com/y-crdt/y-crdt).

**Performance at note-app scale.** No single public number for "10k docs, offline days, merge" was found in this pass for Yjs specifically (their benchmark docs are thinner than Loro's and Automerge's; UNVERIFIED specifics). The structural advantages for this scale are known and verifiable: update-based (delta) sync rather than whole-document serialization, snapshot compaction via `encodeStateAsUpdateV2`, and persistence-friendly updates that can be applied incrementally (https://docs.rs/yrs, https://github.com/yjs/yjs). Yjs's ecosystem historically had a documented large-document load-time problem similar to Automerge 2.x's (solved per-document via snapshots); no public Yjs "17-hour doc" equivalent found; UNVERIFIED.

**License / repo.** Yjs: MIT, https://github.com/yjs/yjs. Yrs: MIT (per repo/crates), https://github.com/y-crdt/y-crdt, https://lib.rs/crates/yrs.

**Real-world adoption.** Yjs is the de facto standard in web editors; it powers large products (documented adopters include Notion's collaborative editing and JupyterLab's pycrdt-based realtime stack (https://y-crdt.github.io/pycrdt/ for the Jupyter-side binding)). I did not re-verify Notion's current use this pass; treat "Notion uses Yjs" as widely reported but UNVERIFIED this pass. The safest verified adoption claim: pycrdt (Jupyter ecosystem) is built on yrs (https://y-crdt.github.io/pycrdt/), and secsync ships production examples on both Yjs and Automerge (https://github.com/nikgraf/secsync).

**Encryption story.** Core Yjs takes no position; there is no built-in E2EE. Community threads from 2020 onward establish the pattern: "how could I add e2ee when using Y.js? Ideally I'd like to put something like a middleware in y-websocket provider" and the workable answer is encrypting updates at the provider/persistence layer because updates are opaque byte strings (https://discuss.yjs.dev/t/implementing-end-to-end-encryption/308). The 2024 thread on "(Y.Text and) end-to-end encryption" shows someone building "a shared DAG with end-to-end encryption... the structure of the DAG (the 'edges') does not have to be encrypted (it consists of random UUIDs anyway) but the actual value of the 'nodes' has to" (https://discuss.yjs.dev/t/y-text-and-end-to-end-encryption/2854). y-webrtc has a room-password option that encrypts WebRTC transport, which is transport-only, not storage E2EE (https://github.com/yjs/y-webrtc). Third-party forks swap in real E2EE transports, e.g. a y-webrtc fork using Trystero's E2EE (https://github.com/WinstonFassett/y-webrtc-trystero). The mature answer for storage E2EE is secsync on top of Yjs (see secsync section) (https://github.com/nikgraf/secsync).

**Pull-from assessment.** For a Rust/Tauri app, yrs is the interesting artifact (native Rust, binary-protocol compatible with the huge Yjs ecosystem, MIT). Integration cost: moderate; you would write your own persistence and sync loop (yrs has sync building blocks in-crate) or reuse y-sync/yrs-sync protocol crates; the JS provider ecosystem does not transfer. Trade-off vs Automerge/Loro: yrs gives the largest ecosystem compatibility and a fast text implementation, with less first-party tooling than automerge-repo or Loro's batteries-included approach (https://github.com/y-crdt/y-crdt, https://docs.rs/yrs).

## 3. Loro

**What it is / who maintains it.** Loro is a Rust-native rich-CRDT engine: "Make your JSON data collaborative and version-controlled with CRDTs... building local-first and collaborative apps easier" (https://github.com/loro-dev/loro). Tagline: "Reimagine state management with CRDTs"; it provides a family of CRDTs (Text with rich-text merge, List, MovableList, Map with LWW sub-models, Tree) over a shared EventGraph (https://loro.dev/). Maintained by the loro-dev org with corporate/community backing; it publishes unusually good engineering documentation.

**Maturity / current status.** Actively developed, fast release cadence; their wire protocol crate `loro-protocol` was published on crates.io as recently as June 2026 (https://crates.io/crates/loro-protocol); the protocol announcement is Oct 2025 (https://loro.dev/blog/loro-protocol). API stability: Loro 1.x is stable for core APIs; bindings exist for JS/WASM (loro-crdt), Swift, Kotlin, Python via loro-ffi (https://github.com/loro-dev/loro, https://docs.rs/loro/). Overall maturity: younger than Yjs/Automerge but no longer experimental; the biggest risk is a smaller production fleet than Yjs.

**Technical profile.** Pure Rust core (docs.rs: Loro documents export/import, incremental updates via `ExportMode::updates(&vv)`, subscription to local updates for streaming over "WebSocket/WebRTC", peer IDs, automatic conflict resolution across all data types) (https://docs.rs/loro/). Distinctive features relevant to a notes app: time-travel/checkout to any version, shallow snapshots (history truncation without losing mergeability), sub-documents, JSONPath query API, and a Fractal String / rich-text implementation designed for concurrent rich-text merges (https://loro.dev/, https://docs.rs/loro/). Performance: Loro publishes a standing benchmark page comparing its JS/WASM build against Automerge and Yjs ("JS/WASM Benchmarks - Loro", https://www.loro.dev/docs/performance); their own data shows Automerge competitive when batching changes into single transactions ("Automerge can perform the B4 benchmark in about 1 second if all changes are applied within a single change transaction") (https://www.loro.dev/docs/performance). Read the benchmark page with the usual vendor-benchmark skepticism; no independent benchmark was located this pass (UNVERIFIED independent numbers).

**Bundle/binary size.** Not captured this pass; the WASM build exists via loro-crdt npm; UNVERIFIED exact size. For the Tauri posture it is a native Rust dep, so bundle size is mostly irrelevant.

**License / repo.** Dual MIT OR Apache-2.0 per repo; https://github.com/loro-dev/loro, https://docs.rs/loro/.

**Real-world adoption.** The strongest direct-to-this-project adoption evidence in the whole lane: IlowObsidianSync (an Obsidian sync plugin) uses Loro as its CRDT engine for vault sync (https://github.com/Ilow-Space/IlowObsidianSync). Also SchoolAI's loro-extended builds LLM-agent state on top of Loro, "treating agents as 'peers' in a CRDT network... subscribe to a document... reactive server-side AI responses that stream directly into Loro Text containers" (https://github.com/schoolAI/loro-extended). No large-scale production postmortem found; UNVERIFIED beyond these.

**Encryption story.** The project itself ships E2EE in its wire protocol: "The Loro Protocol is a wire protocol designed for real-time CRDT synchronization... End-to-end encrypted Loro is included in loro-protocol, but the feature is currently experimental: expect wire formats and key-management APIs to change, and do not rely on it for production-grade security audits yet" (https://loro.dev/blog/loro-protocol, Oct 30, 2025). The Rust crate "Mirrors the TypeScript package... and follows the wire format described in protocol.md and the end-to-end encrypted flow in protocol-e2ee.md" (https://crates.io/crates/loro-protocol). So: yes, document contents can be encrypted before operations hit the wire, first-party, with an honest experimental flag. The core CRDT library itself remains unencrypted-by-default; E2EE lives at the protocol layer.

**Pull-from assessment.** This is the highest-fit CRDT core for a Rust/Tauri notes app that wants E2EE: Rust-native, permissive dual license, batteries included (rich text, sub-docs, time travel), and a first-party E2EE wire protocol to adopt or study even if you outgrow it. Integration cost: low-to-moderate; lorolike API is well documented and the loro-protocol E2EE flow (protocol-e2ee.md) plus Ilow's Loro+AES-256-GCM architecture give two independent blueprints (https://crates.io/crates/loro-protocol, https://github.com/Ilow-Space/IlowObsidianSync).

## 4. Diamond Types

**What it is / who maintains it.** A Rust CRDT for collaborative text by Joseph Gentle (the ShareJS/OT veteran), self-described bluntly: "The world's fastest CRDT. WIP." (https://github.com/josephg/diamond-types). It implements a new text-merge algorithm (informed by Gentle's work on the Perl/RGA family and his "JYuts"? no; his blog series on CRDT lineages), and "This version of diamond types only supports plain text editing. Work is underway to add support for other JSON-style data types" (https://github.com/josephg/diamond-types).

**Maturity / current status.** Explicitly WIP; crates.io package published as v1.0.0 (https://lib.rs/crates/diamond-types), but the README's own status line ("WIP") and the feature scope (text only, JSON types "underway") define real maturity: research-grade, single-maintainer, not hardened for product use (https://github.com/josephg/diamond-types). Issue activity shows open issues through mid-2025 (Jul 2025 latest observed), community size ~1.8k stars (https://github.com/josephg/diamond-types/issues). No release cadence to speak of; treat as a laboratory artifact.

**Technical profile.** Pure Rust; also exposes a JS build under js/ (https://github.com/josephg/diamond-types/tree/master/js). Its published benchmark, "CRDTs go brrr," claims processing 1M transactions in ~4 minutes and positions it as roughly an order of magnitude faster than competing CRDT implementations on large text workloads (https://josephg.com/blog/crdts-go-brrr/, referenced from the repo README as "This blog post on making diamond types 5000x faster than competing CRDT implementations") (https://github.com/josephg/diamond-types). The author's benchmark methodology (fixed seeds, huge generated edit sequences) is public; it is a good methodology to copy for this project's own 10k-doc benchmark, regardless of whether Diamond Types is adopted.

**License / repo.** MIT (per repo); https://github.com/josephg/diamond-types. (License line not explicitly re-captured this pass; MIT is the repo's stated license historically; UNVERIFIED this pass, verify on crates.io page.)

**Real-world adoption.** None found in shipping products this pass; it is cited widely as the state-of-the-art text CRDT benchmark target. UNVERIFIED adoption in any shipped app.

**Encryption story.** None documented. No E2EE guidance in the README or docs located this pass. The algorithm operates on plaintext edit sequences; whether its internal structure can be made ciphertext-friendly is an open question nobody has answered publicly (finding: no evidence found).

**Pull-from assessment.** Concepts only for this project (its algorithmic ideas, especially the benchmark suite and the txlist/branch design), plus possibly as a text-only merge engine if the project ever needs maximum text throughput. Not production-pullable today: single maintainer, WIP, text-only (https://github.com/josephg/diamond-types). MIT license means code pull would be legal if it were ready; it is not.

## 5. Beelay / Keyhive (Automerge's E2EE p2p layer + the Keyhive ecosystem)

**What it is / who maintains it.** Two related layers, one lineage. **Beelay** (automerge org): "an experimental implementation of a new sync protocol for Automerge. In fact, because one of the goals of the project is to produce a sync protocol which allows end-to-end encryption of the document data this protocol will work for any data structure which likes being represented as a hash-linked DAG of changes" (https://github.com/automerge/beelay). Beelay is designed to work over arbitrary transports; over TLS it relies on the hostname binding, and "in other network setups such as P2P transports you will need to obtain the public key of the receiver out of band" (https://www.inkandswitch.com/keyhive/notebook/05/). **Keyhive** is the successor platform: an Ink & Switch project, "local-first access control," which grew out of Beelay work; the automerge org describes it as "our access control and encryption layer for Automerge and other CRDTs" (https://www.inkandswitch.com/project/keyhive/, https://automerge.org/blog/2026-september/). The Rust workspace lives at the Ink & Switch GitHub org: "Rust workspace for Keyhive and related crates... keyhive_wasm: Wasm wrapper around keyhive_core, plus TypeScript bindings. Auth-enabled sync over end-to-end encrypted data lives in a separate repository: Subduction (the successor to Beelay)" (https://github.com/inkandswitch/keyhive).

**Maturity / current status.** Beelay: "This is very much a work in progress, expect things to be very broken and to change significantly before we're done" (the repo's own status line) (https://github.com/automerge/beelay). Keyhive: under active development by Ink & Switch with a public notebook series (05 installments as of March 2025) (https://www.inkandswitch.com/keyhive/notebook/); September 2026 automerge blog reports "Keyhive now has a written threat model and glossary. The threat model sets out who Keyhive defends against, which assets it protects (and which it doesn't), the trust assumptions, and the known gaps between the design and today's code" (https://automerge.org/blog/2026-september/). JS integration exists: `@automerge/automerge-repo-keyhive` provides `initializeAutomergeRepoKeyhive({ createRepo, storage })` (https://github.com/automerge/automerge-repo-keyhive). Verdict: pre-1.0, institutional backing, fast-moving; the most credible open E2EE-CRDT stack, and simultaneously the least settled.

**Technical profile.** Rust workspace (keyhive_core, keyhive_wasm, keyhive_node?; components include the document DAG sync, membership graph, and BeeKEM). Keyhive "generates quite a few encryption keys. Distributing keys to the members of a group concurrently and efficiently is a challenge. [We used the] TreeKEM design to develop BeeKEM, a concurrency-friendly continuous group key agreement (CGKA) mechanism that can be updated concurrently with arbitrary divergence between replicas" (https://www.inkandswitch.com/project/keyhive/). Beelay also performs attestation: "Beelay can ensure that new commits added by the application are attested to by the active peer, and can perform the logic of validating attestations received over the network. This in turn means that the application (Automerge) needs no modifications in order to attest to commits - just call `Beelay.addCommits`" (https://github.com/inkandswitch/keyhive/pull/120). BeeKEM v2 design work includes post-quantum flexibility per the Sep 2026 update (https://automerge.org/blog/2026-september/; detail level as reported there). Performance/binary size at note scale: no public benchmarks found; UNVERIFIED.

**License / repo.** Keyhive workspace: https://github.com/inkandswitch/keyhive (license not explicitly captured this pass; UNVERIFIED, verify before pulling). Beelay: https://github.com/automerge/beelay. Subduction: separate repo, successor to Beelay (https://github.com/inkandswitch/keyhive README).

**Real-world adoption.** Roomy (ATProto chat app) publicly planned to build on Keyhive/Beelay: "one of the biggest reasons that we are planning on using some upcoming work that will be integrated into Automerge: Beehive (soon to be renamed Keyhive) & Beelay. Synchronization: We don't need to implement our own synchronization algorithm" (https://lobste.rs/s/oqfmhj/, Feb 2025). A public PoC combines automerge + Keyhive/Beelay + iroh + Tauri, which is nearly this project's exact stack (https://www.context-awesome.com/list/n0-computer/awesome-iroh). No production postmortems; UNVERIFIED beyond these.

## 11. secsync

**What it actually is (verified).** secsync is an open-source architecture and JS/TS library "to relay end-to-end encrypted CRDTs over a central service," by Nik Graf (Serenity Kit), built out of the need "to have an end-to-end encrypted protocol to allow data synchronization/fetching incl. real-time updates to support local-first apps in combination with a web clients without locally stored data" (https://github.com/nikgraf/secsync). It is NOT a CRDT, NOT a Rust library, and NOT maintained by "veraid"; it is a protocol + TS SDK + reference server, NLnet-funded ("Secsync is proudly sponsored by NGI Assure via NLNet"; project page: Period 2021-08 to 2024-08, "While popular CRDT implementations like Yjs or Automerge offer several designs and even implementations on how to asynchronously exchange data using servers, there is no plug & play implementation serving end-to-end" [encrypted collaboration]) (https://github.com/nikgraf/secsync, https://nlnet.nl/project/Naisho/).

**Maturity / current status.** Beta: "WARNING: This is beta software" (https://github.com/nikgraf/secsync). The NLnet grant period ended August 2024 (https://nlnet.nl/project/Naisho/); the author presented it publicly as recently as March 2026 ("An overview of Secsync - an end to end encryption system for CRDTs" at a local-first talk) (https://guild.host/presentations/secsync-end-to-end-encryption-ttc3oc). Maintenance cadence since the grant ended is unclear; UNVERIFIED current release status.

**Technical profile.** TypeScript/JS SDK + Postgres-backed reference relay + example apps (Yjs example with cursor awareness, Automerge example) (https://github.com/nikgraf/secsync). Architecture, from the README:
- Building blocks: Document (ID + active Snapshot), Snapshot ("includes the encrypted CRDT document at a certain time"), Update ("one or multiple encrypted CRDT updates referencing a snapshot"), Ephemeral message ("includes encrypted data referencing a document").
- Versioning: "the server service persists an update it stores it with an integer based version number which is returned to every client... clients efficiently can ask for only the updates they haven't received."
- Crypto: "Each Snapshot and Update is encrypted using an AEAD constructions. Specifically XChaCha20-Poly1305-IETF. Exchange incl. rotation of the secret key is not part of this protocol and could be done by using the Signal Protocol or lockboxes based on an existing Public key infrastructure (PKI)." Snapshots/Updates also carry unencrypted-but-authenticated metadata (Document ID, Snapshot ID, client public key, per-client clock) and are signed with Ed25519.
- Integrity/trust model: "The central relay service can not inject any participants nor data into a document. The server can completely cut out one user at any point without being detected... Clients have to trust each other." Metadata is NOT hidden: "the relay service is aware on which documents a client has access to and when and how roughly how much someone contributed to a document."
- Key rotation: snapshot re-encryption when a collaborator is removed (requires tombstone support, which Yjs has).
(All quotes from https://github.com/nikgraf/secsync.)

**Performance.** The design rationale is performance-motivated: without snapshots, "documents that are a couple of pages long can include several thousand changes... downloading, decrypting and applying all of them to a CRDT document" is an "UX issue"; planned benchmarks listed as future work (https://github.com/nikgraf/secsync). No published benchmark numbers; UNVERIFIED.

**License / repo.** License not captured on the fetched README this pass; UNVERIFIED (check the repo's license file before any code pull; historically the repo is AGPL-3.0 per its package metadata, UNVERIFIED). Repo: https://github.com/nikgraf/secsync (mirrors at the serenity-kit org: https://github.com/serenity-kit/secsync).

**Real-world adoption.** The worked example is the author's own Serenity Notes, an end-to-end encrypted collaborative notes app built on this stack (documented via the secsync ecosystem pages and the NLnet project page) (https://nlnet.nl/project/Naisho/, https://github.com/nikgraf/secsync). Beyond that, adoption appears minimal; UNVERIFIED.

**Encryption story.** This is the reference blueprint for the exact question this lane was asked: a CRDT that normally needs plaintext ops is combined with E2EE by encrypting whole updates/snapshots as opaque AEAD blobs and letting the relay store only ciphertext, with signatures and clocks on the outside for ordering and authenticity. The cost is spelled out honestly: server sees metadata; clients trust each other; removal detection is weak (https://github.com/nikgraf/secsync).

**Pull-from assessment.** Concepts: very high; this is the cleanest written spec of the envelope-encryption pattern for CRDT sync (Document/Snapshot/Update/version-integer model) and maps directly onto a Rust implementation. Code: JS-only, so concepts-only for this project; the protocol spec in /docs (Specification, Security & Privacy Considerations, Threat Library) is the pullable artifact (https://github.com/nikgraf/secsync, https://www.secsync.com/docs/specification).

## 14. Tailscale (sync-transport context only)

**What it is.** A commercial WireGuard-based mesh VPN: zero-config overlay networks between a user's devices, with NAT traversal and relays (DERP). Clients are open source; the coordination server is proprietary SaaS (the company's own position: "we discussed open sourcing the coordination server" and chose not to for the closed-platform GUIs and control plane; see https://tailscale.com/blog/opensource). Tailscale employs the maintainer of Headscale, an independent community reimplementation of the coordination server (https://tailscale.com/opensource).

**Status/relevance.** Stable, ubiquitous, commercial. For this project it matters only as (a) a transport users may already run (a notes app syncing over a tailnet is private at the transport layer, but that is Tailscale's E2EE, not the app's), and (b) prior art for "dial by identity not address." Licensing: client open source under BSD-family terms historically, moving to a BSL-style license for the client since 2.0 per third-party coverage ("the clients are open source (BSL since 2.0); the controller is open source too but the SaaS dashboard is not" via Headscale-adjacent coverage) (https://pinggy.io/blog/top_open_source_tailscale_alternatives/). Treat exact license of every component as UNVERIFIED this pass; the headline is: coordination plane is proprietary SaaS unless you run Headscale (https://tailscale.com/opensource).

**Pull-from assessment.** Not pullable (proprietary control plane; open-source client, not a library for app-embedded sync). For a zero-knowledge notes app, iroh provides the same dial-by-key + relay pattern as an embeddable library without the external coordination service (https://github.com/n0-computer/iroh). Concept reference only.

## 15. Netbird (sync-transport context only)

**What it is.** NetBird is an open-source WireGuard-based mesh VPN: "NetBird securely connects people, machines and AI agents across any network with one identity-based Zero Trust platform. Powered by peer-to-peer WireGuard" (https://github.com/netbirdio/netbird). "Built on open source technologies like WireGuard, Pion ICE, and Rosenpass" (https://github.com/netbirdio/netbird). Key differentiator vs Tailscale: "NetBird can be fully self-hosted (management server, STUN/TURN, signal server), while Tailscale's coordination server is proprietary" (https://kx.cloudingenium.com/en/netbird-self-hosted-wireguard-mesh-vpn-zero-config).

**Status/relevance.** Actively maintained (repo updated within three weeks of research) (https://github.com/netbirdio/netbird). License: "primarily licensed under AGPLv3, enabling organizations to deploy and audit the complete stack"; the entire coordination infrastructure (management, signal, relay) can be self-hosted (https://netbird.io/knowledge-hub/top-5-opensource-alternatives-to-tailscale2). Rosenpass adds post-quantum key exchange to the WireGuard tunnels (https://github.com/netbirdio/netbird).

**Pull-from assessment.** Not a sync layer; a user-owned transport. AGPLv3 makes code concepts-only for this project. Relevance: if the notes app's relay needs to run only inside a user's private network, NetBird (or any WireGuard mesh) is the transport; the app itself should not embed it. Rosenpass is a nice conceptual pointer for post-quantum transport hardening (https://github.com/netbirdio/netbird).

## 16. IlowObsidianSync (verified; exists, and it is the closest living relative of this project)

**What it actually is.** An Obsidian community plugin plus self-hosted backend: "LoroCRDT based obsidian offline first sync implementation. End-to-end encrypted, real-time sync for your Obsidian vault, backed by a self-hosted Go/PostgreSQL server you control. Notes, plugin settings, themes and binaries stay in sync across devices using a CRDT engine (Loro) for conflict-free merging, while a client-side AES-256-GCM key keeps the server unable to read your content. This is not a hosted service" (https://github.com/Ilow-Space/IlowObsidianSync).

**Maturity / current status.** Young but moving fast: releases 1.5.x through 1.6.x within a short window (observed tags 1.5.4 through 1.6.9, with fixes for "accurate diverged-file push reporting and reconnect self-heal" in 1.6.5 and CRLF/self-plugin-folder divergence fixes in 1.6.3) (https://github.com/Ilow-Space/IlowObsidianSync/releases/tag/1.6.5, https://github.com/Ilow-Space/IlowObsidianSync/releases/tag/1.6.3, https://github.com/Ilow-Space/IlowObsidianSync/releases/tag/1.6.9). Listed on Obsidian plugin stats as "ilow-sync" (https://www.obsidianstats.com/plugins/ilow-sync). Not yet in the official community-plugin directory per the README review; single-maintainer-plus-small-contributor team; production hardening still in progress (divergence-fix release notes are the tell). Bus factor: 1 (UNVERIFIED team size, but release authorship suggests very small).

**Technical profile.** Plugin: TypeScript (runs in Obsidian). Backend: Go binary + PostgreSQL, deployable with a single setup script (Postgres + Go binary + systemd on a Linux host) (https://github.com/Ilow-Space/IlowObsidianSync). Architecture highlights from the README:
- E2EE: "your Master Password never leaves the device. A 256-bit AES-GCM key is derived locally (PBKDF2, SHA-256, 100,000 iterations) and used to encrypt every note, path and settings blob before it is sent to your server. The server only ever stores ciphertext."
- Sync: "a Loro CRDT engine merges concurrent edits (including offline changes) without last-write-wins data loss, using WebSocket push notifications for near-instant propagation between devices."
- Structure awareness: "file/folder renames and moves are reconciled against the vault's virtual file tree instead of being treated as delete+create."
- Onboarding: QR-code multi-device setup copying server URL, API key, and encryption salt.
- Network posture: the plugin contacts exactly one endpoint, your own server; no developer-run account system; API-key auth.
(All from https://github.com/Ilow-Space/IlowObsidianSync.)

**License / repo.** AGPL-3.0 (per repo badge) (https://github.com/Ilow-Space/IlowObsidianSync). Concepts-only for this project per lane rules (no code pull); it is also worth watching for its own zero-knowledge claims to be audited.

**Real-world adoption.** Growing Obsidian self-hosting niche; no production postmortems found; UNVERIFIED user numbers. Its release-note themes (divergence, reconnect self-heal, CRLF mismatch) are a free preview of the failure modes this project will hit at the same layer.

**Encryption story.** The direct answer to the project's key open question, shipped: Loro (a structure-aware CRDT) plus envelope encryption of every blob (notes, paths, settings) before it reaches the relay, with the server reduced to a ciphertext store + WebSocket notify. Note the leak profile: file paths and settings are encrypted, but the server still sees sizes/timing, and key rotation semantics are not documented in what was reviewed (UNVERIFIED: rotation story).

**Pull-from assessment.** Architecture pull, high: this is the project's design, implemented, in public, at note-app scale, with real failure modes in the changelog. Not code-pullable (AGPL). Validation points to copy: AES-256-GCM envelope + PBKDF2 master-password derivation, virtual-file-tree reconciliation for renames, QR onboarding, self-hosted single-script deployment (https://github.com/Ilow-Space/IlowObsidianSync).

## 17. Pull-from summary for the Rust/Tauri + zero-knowledge notes app

Rust-native and directly pullable (permissive license): Loro (MIT/Apache-2.0) as the strongest core candidate given first-party E2EE protocol work plus Ilow as architectural precedent (https://github.com/loro-dev/loro, https://crates.io/crates/loro-protocol, https://github.com/Ilow-Space/IlowObsidianSync); iroh (MIT/Apache-2.0, 1.0) as transport, with self-hostable relay (https://github.com/n0-computer/iroh); automerge (MIT, crates.io 0.12.0) as the alternative core with the Keyhive/Subduction E2EE layer if the project prefers the Ink & Switch lineage (https://crates.io/crates/automerge, https://github.com/inkandswitch/keyhive); p2panda crates (MIT/Apache-2.0), especially p2panda-encryption/-spaces/-auth for group crypto, accepting pre-1.0 churn (https://github.com/p2panda/p2panda); yrs (MIT) as the Yjs-compatible Rust port when ecosystem compatibility matters (https://github.com/y-crdt/y-crdt).

JS-only, concepts/specs only: secsync (the envelope-encryption protocol spec: Document/Snapshot/Update/version-integer, XChaCha20-Poly1305-IETF, Ed25519 signatures, honest threat model) (https://github.com/nikgraf/secsync); BlockSuite (block-model design; y-octo Rust store not production-ready) (https://github.com/toeverything/blocksuite); TanaMigrator (Tana JSON export mapping) (https://github.com/glibalien/tanamigrator).

Concepts-only for license reasons (GPL/AGPL): Cryptomator (vault UX, transparent client-side encryption) (https://github.com/cryptomator/cryptomator); IlowObsidianSync (full Loro+E2EE+Go-relay architecture) (https://github.com/Ilow-Space/IlowObsidianSync); NetBird (self-hosted coordination plane patterns) (https://github.com/netbirdio/netbird).

Research-grade, watch but do not depend: Diamond Types (fastest text CRDT, WIP, single maintainer; benchmark methodology worth copying) (https://github.com/josephg/diamond-types); Beelay (superseded by Subduction) (https://github.com/automerge/beelay).

Skip: diff-match-patch for sync purposes (archived upstream, wrong concurrency model) (https://github.com/google/diff-match-patch); Tailscale as an app-embedded component (proprietary control plane) (https://tailscale.com/blog/opensource).

Recommended reading order for the team, on the E2EE-CRDT question: secsync README/spec first (cleanest written model), then Loro's protocol-e2ee.md, then Keyhive's threat model (https://automerge.org/blog/2026-september/), then any-sync's encrypted-DAG design (https://github.com/anyproto/any-sync), then Ilow's implementation reality (https://github.com/Ilow-Space/IlowObsidianSync), and the practitioner overview (https://kerkour.com/crdt-end-to-end-encryption-research-notes).
